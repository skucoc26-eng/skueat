# 관리자와 이용 통계 구현 명세

## 의존 순서와 검증 책임

1. 로컬: 기존 리뷰 조회/등록과 마이그레이션을 확인한다. 출력은 기존 ID·리뷰를 보존하는 숨김 필드, 감사 이력, 이용 이벤트 테이블이다. 직접 SQLite 회귀 테스트로 확인한다.
2. 로컬: 관리자 인증과 보호된 API를 연결한다. `/admin`, `/api/admin/session`, 로그인/로그아웃, 통계, 리뷰 목록, 리뷰 숨김/복구를 제공한다. 비인증 거절·CSRF·시도 제한·세션 만료를 직접 테스트한다.
3. 로컬: 공개 사이트의 방문·검색·상세·길찾기·룰렛 이벤트와 관리자 화면을 연결한다. 실제 입력어와 식당 클릭은 별도로 집계한다. JavaScript 테스트와 HTTP 통합 검증을 직접 수행한다.
4. 로컬: 전체 테스트·빌드·diff를 검토하고 운영 DB를 백업한 후 배포한다. 운영 인증 경계, 로그인, 통계 조회를 확인하고 검증용 이벤트는 통계에서 제거한다.

## 동작

- 별도 관리자 계정은 환경변수의 사용자명과 bcrypt 비밀번호 해시로 활성화한다. 평문 비밀번호를 저장소나 로그에 남기지 않는다. 관리자 세션은 4시간이며 비밀번호 변경 시 이전 세션은 무효다.
- 리뷰를 숨기면 공개 목록과 평점 집계에서 제외한다. 원문과 사용자별 중복 방지는 보존한다. 복구 시 평점을 재계산한다. 모든 변경에 사유와 관리자·시각을 기록한다.
- 대시보드는 7/30/90일 KST 기준 방문수, 익명 브라우저 수, 일별 추이, 검색어, 식당 상세조회/길찾기/룰렛 순위, 카테고리 및 유입 경로를 보여준다.
- 익명 브라우저 쿠키는 90일이다. IP·카카오 ID와 통계를 연결하지 않는다. 수집을 끌 수 있으며, 원시 이벤트는 90일 보관한다. 클라이언트 이벤트는 광고 차단·쿠키 삭제·봇 등에 영향을 받는 추정치다.
- 과거 로그를 방문자/검색 정답 데이터로 변환하지 않는다. 통계 수집 시작일을 표시한다.

## 테스트 입력과 기대 결과

- 관리자 쿠키 없이 통계/리뷰 변경 → 401, DB 변경 없음. 틀린 CSRF/외부 Origin → 403. 반복 로그인 실패 → 429.
- 1점과 5점 리뷰가 있는 식당 → 1점 숨김 후 공개 1개·평균 5점, 복구 후 공개 2개·평균 3점. 사유 없는 변경 → 400. 숨긴 사용자의 재등록 → 기존 중복 제한 유지.
- 동일 브라우저 방문 2회와 다른 브라우저 방문 1회 → 방문 3·브라우저 2. 검색 `후로` 2회 → 검색 순위 2건. 상세/길찾기/룰렛은 식당 ID별로 독립 집계.
- KST 자정 경계·기간 밖 데이터·90일 만료 데이터·잘못된 식당 ID·허용하지 않은 이벤트·과대 입력을 확인한다.
- 저장된 텍스트의 HTML 실행 방지, 통계 실패가 사이트 기능을 막지 않음, 수집 거부 시 이벤트 전송 안 함을 확인한다.

## 관리자 보완 회귀 명세 (이슈 #40–43)

1. 직접 구현: `/logout`과 `/api/admin/logout`에서 공통 관리자 토큰 폐기를 사용한다. 일반 로그아웃은 기존 카카오 세션 삭제·302 응답을 유지한다. DB 폐기에 실패하면 성공으로 응답하지 않는다. 운영 DB 마이그레이션은 없다.
   - 입력: 관리자 로그인 → 쿠키 복사 → 일반 로그아웃 → 복사 쿠키로 통계 조회. 기대: 302 후 401, 관리자 DB 토큰 삭제.
   - 입력: 관리자 토큰 삭제 DB 오류. 기대: 500, 성공 리다이렉트 없음. 관리자 미사용 사이트의 일반 로그아웃은 기존 동작 유지.
2. 직접 구현: 실패 제한을 접속 IP별 분당 10회로 분리한다. 쿠키를 새로 받아도 같은 IP의 제한은 유지한다. Fly 환경에서만 Fly Proxy의 `Fly-Client-IP`를 사용하고, 그 외에는 소켓 IP를 사용한다. 만료 정보 삭제와 최대 1,024개 항목으로 메모리를 제한한다. bcrypt 검증은 기존처럼 직렬 처리한다.
   - 입력: A IP에서 실패 10회 → A의 쿠키 변경·전달 헤더 변경 → 정상 자격 증명 제출. 기대: 계속 429.
   - 입력: 같은 서버의 B IP에서 정상 로그인. 기대: 200. 1분 만료 후 A의 정상 로그인도 200.
   - 입력: Fly 환경의 서로 다른 유효한 Fly-Client-IP. 기대: 제한 분리. 일반 환경의 위조 전달 헤더는 무시.
   - 한계: 같은 공인 IP를 쓰는 접속자는 제한을 공유한다. 현재 단일 서버의 메모리 제한이며 재시작하면 초기화된다.
3. 직접 구현: 관리자 리뷰 조회에 기존 통계/식당 조회와 같은 요청번호 검사를 적용한다. 요청 당시 페이지로 페이지 표시·버튼을 갱신한다.
   - 입력: 전체 A → 숨김 B 조회, 응답 B → A. 기대: 숨김 B 유지.
   - 입력: 1페이지 A → 2페이지 B 조회, 응답 B → A. 기대: 2페이지 결과·페이지 표시·이전/다음 상태 유지.
4. 직접 구현: GPS의 거리 정렬 갱신에서는 검색 이벤트를 기록하지 않는다. 사용자 검색 제출은 기존처럼 기록한다.
   - 입력: `후로` 검색 1회 → GPS 성공(지도 SDK 있음/없음). 기대: 목록 갱신 2회, 검색 이벤트 1회.
   - 입력: 사용자가 같은 검색을 다시 제출. 기대: 검색 이벤트 총 2회.
5. 직접 검증: 구현 전 위 실패를 확인하고, 수정 후 Go 전체 테스트·JavaScript 전체 테스트·빌드·diff를 검토한다. 운영 DB나 통계에 재현용 데이터를 넣지 않는다.
6. 앞선 운영 반영 요청에 따라 검증한 변경을 푸시하고 자동 배포 결과를 확인한다. 실제 운영 로그인과 일반 로그아웃 후 복사 쿠키의 401을 확인한다. 운영 리뷰 관리 작업이나 비밀번호 실패 재현은 하지 않는다.
